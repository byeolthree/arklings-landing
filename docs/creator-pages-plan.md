# 크리에이터 화면·데이터 계획 (고친 판: 2026-10-31, `design` 가지)

아직 코드는 하나도 고치지 않았다. 이 계획을 승인받은 뒤에 만든다.
근거: `docs/screen-contract.md`, `docs/portfolio-requirements.md`, 현재 코드(`dev` e090abb 기준), Figma 캡처 2장(「크리에이터 포트폴리오 탐색」, 「크리에이터 프로필」).
바뀐 지시: 백엔드를 건드리지 않는다는 규칙은 **크리에이터 데이터에 한해** 풀린다. 크리에이터와 관계없는 백엔드는 그대로 건드리지 않는다.

## 0. 구조 (별뜨리님이 정한 대로)

- 크리에이터가 기획안을 **공개하면** 그 기획안이 그 크리에이터의 **포트폴리오**에 올라간다. 따로 `participations` 표는 만들지 않는다.
- 크리에이터는 기획안을 공개하는 **과정에서 프로필도 만든다**(공개 주소, 역할, 소개).
- 「크리에이터」 메뉴 → **크리에이터 목록** → 크리에이터 한 명 → **그 사람의 프로필 + 포트폴리오**(그 사람이 공개한 기획안들) → 기획안 하나 → **기획안 상세** → 「협업 신청」.

```
「크리에이터」 메뉴 ─▶ /creators (목록) ─▶ /creators/<공개주소> (프로필 + 포트폴리오)
                                                   │
                                                   ▼
                                       /portfolio/<기획안 번호> (상세) ─▶ 「협업 신청」 /collab/new?plan=
기획안 화면 /planner ─ 「포트폴리오에 올리기」 ─▶ (프로필이 없으면 프로필 만들기) ─▶ 공개
```

## 0-1. 화면 규칙 (별뜨리님 지시, 2026-10-31 고침)

- 목록 위쪽에는 **제목과 설명 문구만** 둔다(랜딩 히어로처럼 옅은 띠 위에). **제목 위에 따로 얹는 작은 글(kicker)은 두지 않는다.**
- 프로필·기획안 상세의 위쪽 구성은 그 화면을 만들 때 같은 방식(제목, 설명만)으로 보여 드리고 확인받는다.
- 오류 화면(오류·404)은 무슨 일인지 알려 주는 제목을 둔다.
- 샘플 미리보기의 안내 상자는 사이트에 없는 도우미일 뿐이다(오른쪽 아래에 작게 띄우고, 미리보기 주소를 지울 때 함께 사라진다).

## 1. 먼저 알아 둘 사실

1. 「크리에이터」 메뉴는 지금 글자일 뿐 눌러도 이동이 없다(`public/landing.html` 1063·1072번째 줄, `components/site-nav.tsx`).
2. 지금 `/portfolio`는 "공개된 기획안 전체 목록"이고 카드 한 장이 기획안 한 건이다. 새 구조에서는 **크리에이터 한 명이 카드 한 장**인 목록이 `/creators`가 된다.
3. `profiles`는 **누구나 읽을 수 있는 표**다(0002의 `profiles read all`, 로그인 없는 사람 포함). 여기에 공개 주소·역할·소개를 그냥 칸으로 더하면, 기획안을 한 건도 공개하지 않았거나 공개를 모두 끈 사람의 프로필도 누구나 읽을 수 있게 된다. → 4번의 설계로 막는다.
4. SQL은 0002까지만 실행돼 있다. 0003~0008을 실행하기 전에는 실제 데이터 화면과 공개 과정은 이 맥에서 **동작을 확인할 수 없다.** 화면 모양은 샘플 미리보기로 본다.
5. 시안(Figma)의 상단 메뉴는 랜딩과 다르다. 시안과 랜딩이 다르면 랜딩을 따른다.

#### 3-1-1. 목록의 검색바와 역할 필터 (별뜨리님 지시, 2026-10-31)

- **검색바:** 한 줄 입력칸 + 「검색」 버튼. 주소의 `?q=`로 간다(로그인 없이, 글자 입력만, 30자까지). 찾는 범위는 카드에 보이는 글(공개 이름, 크리에이터 한 줄 소개, 대표 기획안 제목·한 줄 소개)이다. 눈에 안 보이는 공개 주소(handle)는 찾지 않는다.
- **역할 필터:** 검색바 옆의 「필터」 버튼을 **눌러야** 선택지가 펼쳐진다(평소에는 칩이 보이지 않는다). 골라 둔 역할이 있으면 버튼에 숫자(1)가 붙는다. 선택지는 「전체」 + 협업 신청의 `ROLES` 6개(영상 제작·대본·아트디렉터·역사 자문·책임 프로듀서·기타)이고 **하나만** 고른다(`?role=`). 모르는 값은 무시한다. 검색어와 함께 쓸 수 있다.
- 검색어나 역할을 바꾸면 1쪽부터 다시 본다(쪽 번호를 이어 가지 않음). 쪽 이동에서는 검색어·역할을 유지한다.
- 걸린 조건이 있으면 개수 줄이 「검색 결과 N명 · 조건 지우기」로 바뀐다.
- 새 경우: **조건에 맞는 크리에이터가 없음**(「맞는 크리에이터가 없어요」 + 「조건 지우기」). 크리에이터가 아예 없는 경우(「아직 크리에이터가 없어요」)와 구분한다. 조건이 있는데 쪽 번호만 너무 큰 경우는 「첫 쪽으로」가 같은 조건의 1쪽으로 간다.
- 자바스크립트 없이 주소(GET)만으로 동작하므로 새로고침·링크 공유가 된다.
- **색:** 자주색(주 색)은 「검색」 「기획안 만들기」 같은 핵심 버튼에만 쓰고, 나머지 강조(선택된 필터, 보조 버튼, 링크)는 청록을 쓴다. **프로필 원은 보조 색 세 가지(청록·더스티 블루·뮤트 세이지)를 목록 순서대로 번갈아 쓰고**(줄마다 한 칸씩 밀어 이웃 카드와 겹치지 않게), **카드 아래의 태그는 「기획안 N건」이 아니라 그 사람의 역할 태그**이며, 역할마다 다른 색이고 같은 역할은 늘 같은 색, 글자는 모두 흰색이다. 색은 컬러 시스템에서 **상태(semantic) 색, 제목 색, 배경 색을 뺀 나머지만** 쓴다(대본 청록 / 영상 제작 더스티 블루 / 아트디렉터 황금 / 역사 자문 뮤트 세이지 / 책임 프로듀서 자주 / 기타 본문색 `#574A50`. `components/creators/role-tone.ts`). **이름 아래에는 역할 글을 두지 않고 크리에이터를 소개하는 한 줄 문구(`bio`)를 한 줄로 보여 준다**(`bio`가 없으면 그 줄은 숨김). 필터 버튼은 자주색 테두리·글자·아이콘이고 마우스를 올리거나 펼쳐도 색이 바뀌지 않는다. 검색바와 버튼(검색, 필터)은 가운데 정렬이다. 카드 안 「대표 기획안」 칸의 배경은 원래대로 페이지 배경색(`#FAF7F8`)이다. 상단 메뉴의 「크리에이터」 강조도 자주가 아니라 제목 색이다.
- **카드:** 크리에이터 카드에는 외곽선을 두지 않는다(그림자와 옅은 면으로만 구분).
- **배경:** 기본 배경색은 랜딩과 같은 `#FAF7F8` 그대로 지킨다(색 얼룩·바탕 그라데이션은 쓰지 않는다 — 별뜨리님 지시). 위쪽 띠에만 랜딩 히어로 배경과 옅은 점 무늬를 둔다.
- **백엔드 대응(7단계):** `listCreators(page, { q, role })`가 `creators_public` 보기에서 `roles @> {role}`와 `name`·`bio`·대표 기획안 제목·한 줄 소개의 부분 일치(`ilike`, 검색어의 `%`·`_`는 글자로 처리)로 거른다. 입력 정규화는 `components/creators/filter.ts`의 `parseFilter`를 그대로 쓴다.

### 3-3. 기획안 상세 `/portfolio/<id>`

| 경우 | 나오는 화면 |

| 공개된 기획안 | 제목, **작성자(이름·역할, 누르면 프로필)**, 게시일, 로그라인, 질문별 답, 「이 기획안에 협업 신청」, 링크 복사 |

| 긴 이름·긴 로그라인·빈 답 | 줄바꿈·말줄임 처리, 빈 칸은 숨김 |
| DB 오류 / 읽는 중 | 오류·로딩 화면 |

### 3-4. 「협업 신청」을 눌렀을 때 (디자인은 안 건드림)

| 경우 | 결과 |
|---|---|
| 공개 중 | `/collab/new?plan=<id>` 폼 + 「○○님께 전달됩니다」 |
| 그 사이 공개가 꺼짐 / 지워짐 | 「신청할 수 없는 기획안이에요」 + 「포트폴리오 둘러보기」(링크를 `/creators`로 바꿀지 D2에서 정함) |
| 취소 | 그 기획안 상세로 돌아옴 |
| 접수 성공 | `/collab/done`. 지금은 0003이 없어 **보내기는 안 됨** |
| 자기 기획안에 자기가 신청 | 코드상 막는 곳이 없다. 이번 범위에서는 그대로 |

### 3-5. 공개 과정에서 프로필 만들기 (`/planner`)

| 경우 | 나오는 화면·동작 |
|---|---|
| 로그인 안 함 | 지금과 같음(저장·공개는 로그인 필요 안내) |
| 로그인 + 이메일 확인 전 | 지금과 같음(`/auth/add-email`로 이동) |
| 로그인 + **프로필 없음** + 「포트폴리오에 올리기」 | 먼저 프로필 만들기 칸(공개 주소, 역할, 소개)이 열림. **칸 위에 항상 보이는 안내 한 줄: 「이 프로필은 누구나 볼 수 있습니다」**(접거나 숨길 수 없고, 저장 버튼 위에 둠). 저장하면 이어서 공개됨 |
| 로그인 + 프로필 있음 | 지금처럼 바로 공개 |
| 공개 주소가 이미 쓰는 중 / 형식 틀림 / 예약어 | 칸 아래에 이유 표시 |
| 역할을 하나도 안 고름 / 소개가 200자 초과 | 칸 아래에 이유 표시 |
| 공개를 끔 | 기획안만 내려감. **프로필은 남는다**(목록·프로필 화면에서는 공개한 기획안이 없으면 안 보임) |
| 프로필 고치기 | 같은 패널에서 역할·소개를 고침. 고치는 칸에도 같은 안내 한 줄이 보임. **공개 주소는 한 번 정하면 바꾸지 않는다**(D5) |
| 회원 탈퇴 | 프로필도 연쇄 삭제(0008이 `auth.users`에 연쇄로 묶음) |
| 공개 안내 문구 | 프로필 칸의 안내 한 줄(위)은 **크리에이터 화면 안의 안내**라서 이번 범위에 넣는다. 기획안 화면에 이미 있는 「올리면 공개 이름과 완성 내용이 보인다」 문장에도 **공개 주소·역할·소개도 보인다**를 더한다. 이용자 동의 문구(`lib/consent.ts`)와 `/privacy`는 바꾸지 않는다(위험 참고) |

### 3-6. 화면 크기

| 크기 | 목록 | 프로필 | 상세 |
|---|---|---|---|
| 데스크톱 1440 | 카드 3열, 좌우 여백 80px | 이름 영역 + 포트폴리오 3열 | 가운데 1040px |
| 태블릿 768~1023 | 2열 | 2열 | 같음 |
| 모바일 375 | 1열, 좌우 여백 16px, 햄버거 메뉴 | 1열 | 한 열, 버튼 가로 가득 |

나눔점은 랜딩과 같은 768 / 1024. 한 화면을 만들 때마다 1440과 375를 모두 보여 준다.

## 4. 데이터·백엔드 (크리에이터 데이터에 한해)

**실행은 하지 않는다.** `supabase/migrations/0008_creators.sql` 파일만 만든다. 순서는 0001~0007과 같다: `main`에 새 코드를 올린 뒤 별뜨리님이 SQL Editor에서 0007 다음에 0008을 실행한다. 여러 번 실행해도 안전하게 쓴다(`if not exists`, `create or replace`).

### 4-1. 표와 보기

| 대상 | 내용 | 주의 |
|---|---|---|
| **새 표 `creator_profiles`**(제안: `profiles`에 칸을 더하는 대신 분리) | `user_id`(→`auth.users`, 탈퇴하면 연쇄 삭제), `public_handle`, `roles text[]`, `bio`, `created_at`, `updated_at` | `profiles`가 누구나 읽는 표(1번 사실의 3)라서, 칸을 더하면 비공개여야 할 프로필이 노출된다. 표를 따로 두고 읽기 권한을 좁힌다. **이전 제안의 `profiles.public_handle` 방식에서 바뀌는 점이라 승인이 필요하다(D1).** |
| `public_handle` 규칙 | 영문 소문자·숫자·하이픈, 3~20자, 처음·끝 하이픈 금지, 대소문자 구분 없이 중복 금지(고유 색인), 예약어(`new`, `edit`, `admin`, `api` 등) 금지. DB가 `check`와 고유 색인으로 막고, 서버도 같은 규칙으로 먼저 검사 | |
| `roles` 규칙 | 1개 이상 6개 이하, 값은 `video`·`script`·`art_director`·`history_advisor`·`producer`·`other`만(DB `check`) | 협업 신청의 `ROLES`와 같은 목록을 쓴다 |
| `bio` 규칙 | 0~200자(선택), `<` `>` 제어문자 금지(공개 이름과 같은 검사) | |
| 읽기 권한 | `creator_profiles` 표 자체는 **본인만 읽고 쓰기**(RLS). 누구나 보는 길은 보기(view)로만 | 이메일·주인 번호는 보기에 넣지 않는다 |
| 새 보기 `creators_public` | `public_handle`, `display_name`, `roles`, `bio`, 공개 기획안 수, 최근 공개한 기획안 제목·한 줄 소개. **공개된 기획안이 1건 이상인 사람만** 나온다. 주인 번호(UUID)는 내지 않는다 | 프로필이 있어도 공개한 기획안이 없으면 읽히지 않는다(3-2의 404) |
| `portfolio_items` 보기 갱신 | `author_handle`(그 사람의 공개 주소) 칸을 더한다. 프로필이 없으면 비어 있다 | 0007이 만든 보기를 `create or replace`로 고침 |
| 공개 조건 | `plans`를 공개(`is_public = true`)로 바꿀 때, 그 주인의 `creator_profiles`가 없으면 DB 트리거가 막는다(오류 코드 `creator_profile_required`) | 앱을 거치지 않고 DB를 직접 열어도 못 올림(0007의 "이메일 확인" 규칙과 같은 방식) |

### 4-2. 코드 (모두 크리에이터 데이터 관련 파일만)

## 6. 만드는 순서 (한 화면씩, 만들 때마다 1440·375로 보여 줌)

1. 메뉴 연결(랜딩 + 사이트 메뉴)
2. 크리에이터 목록(샘플 미리보기)
3. 크리에이터 프로필 + 포트폴리오
4. 기획안 상세(작성자 줄에 프로필 링크)
5. 상태 화면(빈 목록·404·오류·로딩)
6. 공개 과정의 프로필 만들기(`/planner`)
7. 백엔드: `0008_creators.sql`, `lib/creators.ts`, `app/actions/creators.ts`, `setPlanPublic` 수정을 쓰고, 샘플 대신 실제 읽기로 연결. **이 단계는 `npm run build`와 `npm run lint`까지만 확인할 수 있다.** DB가 없어 실제 동작은 확인하지 못한다
8. `docs/screen-contract.md`에 새 화면·함수 줄 추가

각 단계 끝에서 보여 주고 승인받은 뒤 다음으로 간다.

## 7. 위험·한계

- **SQL을 실행하지 않으므로 공개 과정·크리에이터 목록·프로필의 실제 저장과 읽기는 검증하지 못한다.** 샘플 화면은 모양 확인용이고, 실제 데이터와 다르게 보일 수 있다(긴 이름 등은 디자인에서 처리).
- **공개 범위·개인정보:** 크리에이터 프로필(공개 주소·역할·소개)이 누구에게나 보이게 된다. 프로필 칸이 열릴 때 「이 프로필은 누구나 볼 수 있습니다」 안내 한 줄을 화면에 둔다(동의 문구 변경이 아닌 화면 안내). 다만 이용자 동의 문구(`lib/consent.ts`)와 `/privacy`가 이 공개를 충분히 설명하는지는 별뜨리님·전문가 확인이 필요하다. 동의 문구를 바꾸면 `CONSENT_VERSION`을 올려야 해서 이번에는 바꾸지 않는다.
- **공개 조건 트리거**는 새 번호(0008)에만 두므로 0007 이후에 실행해야 한다. 0004~0007을 먼저 실행하지 않으면 0008이 실패한다.
- 이미 공개된 기획안이 0008 이전에 있다면(지금 운영 DB에는 `plans`가 없어 없음) 프로필이 없어 크리에이터 목록에 안 나온다.
- 주인/남을 구분하는 기능(목록에서 "내 것" 표시, 자기 기획안에 신청 막기)은 이번에도 하지 않는다.
- `app/actions/plans.ts`는 기획안 저장·PDF·메일도 함께 담은 파일이다. 고치는 곳은 `setPlanPublic` 하나로 한정하고, 나머지 동작은 건드리지 않는다.
