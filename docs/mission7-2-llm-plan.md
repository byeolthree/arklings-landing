# 미션7-2 계획: 아클링스 AI 기능 (평가 + 라이브러리 질의응답)

작성: 계획 세션(Claude), 2026-11-07. 검수: 아키텍터. 구현: 클로드 코드(웹).
이 문서는 저장소 `docs/`에 있고, 프로젝트 "미션7"에도 같은 내용이 올라가 있다. 두 곳이 어긋나면 저장소 쪽을 기준으로 하고, 고칠 때는 두 곳을 함께 고친다.

## 0. 읽는 순서와 표시 약속

- 먼저 `AGENTS.md`, `CLAUDE.md`를 읽고, 코드를 쓰기 전에 `node_modules/next/dist/docs`의 해당 부분을 읽는다.
- 표시: **[정함]** 아키텍터가 직접 정한 것. **[제안]** 계획 세션이 근거를 달아 제안했고 아키텍터 확인을 기다리는 것. **[열림]** 아직 정해지지 않아 구현 전에 아키텍터에게 묻는 것.
- 근거 표기: "교재 10-x"는 부트캠프 10부 문서, "공고"는 미션7 공고문.

## 1. 목적과 한 줄 요약

- 미션7은 두 갈래다. 7-1은 유저 기능(로그인·기획안 저장, 이미 대부분 붙어 있음), **7-2는 OpenAI 기능**이다. [정함]
- 7-2의 목적: 기획안 작성 중인 사용자가 **아클링스의 질문 기준과 아클링스의 자료 안에서만** 점검받고 답을 얻게 한다. 일반 GPT에 물으면 아클링스가 쓰지 않는 시대·설정이 섞이는 한계를 메운다.
- 이번에 만드는 것은 두 가지다. 둘 다 이번 범위다. [정함]
  1. **AI 평가**: 로그라인 화면에서 사용자가 요청하면 다섯 칸을 기준에 따라 점검한다.
  2. **라이브러리 질의응답**: 아클링스 위키에 있는 내용으로 AI가 답한다. 답 아래에 근거 자료 이름을 보인다.
- 제출물: 공개 GitHub 저장소 + Vercel 배포 주소 (공고).

## 3. 계획 세션의 제안 (아키텍터 확인 대기)

| 번호 | 제안 | 이유 |
|---|---|---|
| P1 | 횟수 제한은 **기능별로 따로, 하루(한국 날짜) 5회**를 임시값으로 둔다. 비용을 재 본 뒤 아키텍터가 숫자를 정한다 | 이미 있는 메일 하루 3번 제한(`mail_usage`)과 같은 검증된 모양을 복사할 수 있다 |
| P2 | 사용 기록 표에 "소비 단위" 칸을 둔다. 지금은 호출 1회 = 1단위 | 나중에 크레딧 방식(코치님 권유)으로 바꿀 때 한도 숫자만 바꾸고 잔액 표만 더하면 된다. 크레딧은 "다 쓴 뒤 어떻게 더 얻나"가 결제(미션 11)와 이어져서 지금은 정해진 답이 없다 |
| P3 | 위키는 Supabase 표에 두고, `공개 여부`가 켜진 항목만 읽기 규칙(RLS)으로 열고, 로그인 없는 방문자도 읽을 수 있게 한다(게시 Q&A 목록용). 서버가 질문을 처리할 때도 같은 규칙으로 읽는다(`createAuthClient`). 쓰기 규칙은 만들지 않는다 (Grok의 "Supabase에 둔다"는 권유와 같은 방향) | 아키텍터가 Q&A 글로 게시할 내용이라 공개 항목은 읽혀도 괜찮고, 공개 전 항목은 DB가 막는다. `AGENTS.md`가 서버 전용 열쇠를 새 읽기에 쓰지 못하게 하므로 그 열쇠가 필요 없다 |
| P4 | 위키가 작을 때는 선택한 항목을 프롬프트에 통째로 넣는다. 커지면 질문과 가까운 항목만 골라 보내는 검색 방식(RAG)으로 바꾼다 | 교재 10-2·10-7의 자료 중심 원칙. 지금 만드는 검색 장치는 과하다 |
| P5 | 평가 결과는 기획안 내용과 **별도 표**에 저장한다 | `plans.public_content`(공개 사본)에 평가가 섞이면 안 되고, 그 사본은 20000바이트 제한이 있다 |
| P6 | 모델 이름은 환경변수 `OPENAI_MODEL`, 호출은 AI SDK로 한다 | 정식 서비스 때 공급자·모델이 바뀌어도 코드를 거의 안 고친다 |

## 4. 지금 MVP와 이어지는 자리

- `/planner`의 단계 탭은 지금 로그라인 하나다 (`components/planner/planner-editor.tsx`). 평가 버튼은 로그라인 화면에 붙인다.
- `lib/plans.ts`의 `SECTIONS`는 `logline` 하나다. 평가 기준은 페이지(섹션) 단위로 갈아 끼우는 구조로 만든다. 다음 페이지가 생기면 기준 문서와 위키 항목만 더한다.
- 질문·팁·금지 예·확인 질문 21개(`CHECK_COUNT`)는 `components/planner/questions.ts`에 있고, 아키텍터가 준 문서에서 나온 문구다. 평가 기준으로 서버가 함께 넘긴다.
- 기존 `buildSuggestion()`(로그라인 문장 틀)은 이번에 바꾸지 않는다. 평가는 그 옆에 붙는 별도 기능이다.
- 상단 메뉴에 "라이브러리"가 있지만 지금은 글자뿐이고 이동이 없다 (`components/site-nav.tsx`, `docs/click-check.md`). 질의응답 화면은 새로 만든다.
- 로그인·복귀 주소·세션은 7-1에서 만든 것을 그대로 쓴다. 비로그인 사용자가 버튼을 누르면 모델 호출 전에 로그인 안내를 보인다.

## 5. 기능 1: AI 평가

**사용 흐름**: 사용자가 로그인한다 → 다섯 칸(사건·주인공·장애물·목표·위험)을 채운다 → "평가 받기"를 누른다 → 칸별 결과를 읽는다 → 글은 사용자가 직접 고친다.

- 다섯 칸이 모두 채워졌을 때 버튼이 켜진다. 빈 칸이 있으면 버튼을 끄고 이유를 문장으로 안내한다.
- 입력: 다섯 칸의 글, 예/아니오 21개 값, 기준 자료. 저장 여부와 관계없이 이번 요청에 내용을 실어 보낸다.
- 출력(Zod 스키마로 모양을 고정한 JSON): 칸마다 `칸 이름`, `상태(충족/보완 필요)`, `이유(1~2문장)`, `고칠 점(질문 한 문장)`.
- 평가는 제안이다. 사용자의 기획안 글을 자동으로 바꾸지 않고, 저장·공개 버튼도 대신 누르지 않는다.
- 모델은 한 번에 끝나는 생성(`generateText` + `Output.object`)으로 호출한다. 서버 동작은 `app/actions/`에 두고 맨 위에서 로그인·이메일 확인을 다시 한다 (`AGENTS.md`).
- 이미 정해진 예/아니오 값은 모델이 다시 계산하지 않는다. 서버가 자료로 넘긴다.
- 결과는 별도 표에 저장한다: 사용자, 섹션, 입력 사본, 결과, 모델 이름, 토큰 사용량, 완료 사유, 시각. 사용자는 자기 결과만 읽는다.

## 6. 기능 2: 라이브러리 질의응답

**사용 흐름**: 로그인한 사용자가 라이브러리에서 질문한다 → 서버가 위키에서 관련 항목을 고른다 → AI가 그 항목 안에서 답을 조금씩 보여 준다 → 답 아래에 근거 자료 이름이 뜬다.

- 자유 챗봇이 아니다. 답은 서버가 고른 위키 항목 안에서만 만든다.
- 근거 자료 이름은 **서버가 고른 항목에서 읽어 와서** 보인다. 모델이 쓴 글에서 가져오지 않는다.
- 위키에 관련 항목이 없으면 모델을 부르지 않고 "이 자료에는 없음"을 보인다 (비용 절약).
- 위키 표가 비어 있어도 화면과 서버가 정상 동작해야 한다. 빈 상태 문구: "아직 준비된 자료가 없어요."
- 답은 `streamText` + `@ai-sdk/react`(`useChat`)로 조금씩 보인다. Route Handler는 POST만 받고, 맨 위에서 로그인·이메일 확인과 요청 출처(`Origin`) 확인을 직접 한다. Server Action과 달리 이 확인이 기본으로 붙지 않는다.
- 답이 도중에 끊기면 "답변을 마치지 못했어요"를 보이고 원래 질문을 남긴다. 완성된 답처럼 보이지 않게 한다 (교재 10-5).
- 질문 칸은 로그인한 사람만 쓴다 (D11). 로그인하지 않은 방문자에게는 게시 Q&A 목록과 로그인 안내를 보인다. 하루 한도는 평가와 같은 방식으로 기능별로 따로 센다 (P1).
- 라이브러리 화면 위쪽에 게시 Q&A 목록(공개 위키 항목), 아래쪽에 질문 칸과 답 영역을 둔다. 배치의 세부는 화면 합의 때 정한다.

## 7. 위키 (LLM wiki)

- 형태: 질문 하나 + 답 하나 + 원문 이름(출처)이 한 줄(한 항목)이다. NotebookLM에서 만든다. [정함]
- 보관: Supabase 표(P3). 공개 항목만 읽기 허용, 쓰기 규칙 없음. 항목은 아키텍터가 Supabase 화면에서 넣는다.
- 표 모양(칸 이름은 구현 때 확정): 항목 ID, 질문, 답, 출처 이름, 시대 표시(열국시대~삼한일통기), 공개 여부, 만든 시각.
- 열림 [열림]: 위키 파일 형식(CSV/마크다운/JSON)과 항목 수는 아키텍터가 정한다. 형식이 정해지기 전까지 구현은 "빈 표에서도 동작"과 "예시 항목 3개 넣기"까지만 만든다.

## 8. 서버 규칙 (모든 AI 호출 앞에 순서대로)

1. 로그인 확인 → 안 되었으면 모델 호출 없이 로그인 안내를 돌려준다.
2. 입력 검사 → 빈 입력, 길이 초과(`MAX_SLOT_CHARS`=200, `MAX_TEXT_CHARS`=1000 등 기존 상수 재사용), 잘못된 형식을 거절한다.
3. 클라이언트가 보낸 `system` 역할 메시지는 거절한다. 허용하는 메시지 종류와 필드는 서버가 골라 읽는다 (교재 10-2, 10-3).
4. 오늘 자리 하나 잡기 → DB 함수 한 번에 "확인과 증가"를 같이 처리한다 (이를 원자적이라 한다. 동시에 여러 번 눌러도 횟수가 새지 않는다). 한도가 찼으면 안내만 돌려준다.
5. 모델 호출. 사용자 글은 "자료"로 감싸 넘기고, 사용자 글 안의 지시를 따르지 않는다. 역할 지침은 서버 파일 `lib/prompts/`에 둔다 (AI SDK 7의 `instructions`).
6. 호출이 실패하면 잡은 자리를 돌려준다 (`mailPlanPdf`의 reserve → release 모양). 결과를 받았으면 자리를 돌려주지 않는다.
7. 완료 사유(`finishReason`)와 토큰 사용량을 기록한다. 키와 사용자 글 전문은 로그에 남기지 않는다.

- 자리 잡기·돌려주기는 `supabase/migrations/0004_plans.sql`의 `reserve_plan_mail` / `release_plan_mail`과 같은 구조로 만든다 (새 마이그레이션 파일). 사용 기록 표는 정책 없이 RLS를 켜서 앱이 직접 못 만지게 한다. 기능 이름을 기본키에 넣어 기능별로 센다.
- 서버 전용 열쇠(`SUPABASE_SERVICE_ROLE_KEY`)는 AI 기능에 쓰지 않는다 (`AGENTS.md` 규칙 4). 사용 기록은 자리 잡기 함수로만, 평가 결과는 로그인한 본인의 권한(RLS)으로 본인 것만 읽고 쓴다.
- 재시도는 `maxRetries: 0`으로 두고, 서버 전체 시간 상한(`maxDuration`)을 정한다.
- 시대 고정(D10): 열국시대~삼한일통기. 자료에 없는 고구려·백제·신라 궁궐·연도·숫자는 지어내지 않고 "확인 필요" 또는 "자료에 없음"으로 답한다.

## 9. 화면의 대기·오류·빈 상태 (공고 심화 1)

| 상황 | 화면에 보이는 것 |
|---|---|
| 로그인 안 함 | 로그인 안내 + 복귀 주소 유지 |
| 빈 칸 있음(평가) | 버튼 꺼짐 + 어느 칸이 비었는지 |
| 입력 너무 김 | 글자 수 안내 |

| 서버 키 없음·잘못됨(401) | "AI 연결에 문제가 있어요. 잠시 뒤 다시 시도해 주세요." 내부 오류·키는 노출하지 않는다 |
| 모델 한도 초과(429) | "지금 요청이 몰려 있어요." (횟수 소진과 다른 문구) |
| 일시 오류·시간 초과 | 다시 시도 버튼. 같은 요청의 중복 비용 가능성을 서버가 확인한다 |
| 호출 중 | 무슨 일이 일어나는지 문장으로 (예: "기준에 맞춰 읽는 중이에요") |
| 질의응답 위키 비어 있음/관련 항목 없음 | "아직 준비된 자료가 없어요" / "이 자료에는 없음" |
| 답이 끊김 | "답변을 마치지 못했어요" + 원래 질문 유지 |

화면은 `public/landing.html`의 디자인 기준(색 토큰: 주색 `#A61E5C`, 보조 `#1F5A66` 등)을 따르고, 색이 바뀌는 hover는 넣지 않는다.

## 10. 환경·패키지·보안 (공고 심화 4)

- 패키지: `ai`, `@ai-sdk/openai`, `@ai-sdk/react`, `zod`. 교재 10-4 기준 AI SDK 7. 새 코드는 현재 이름(`instructions`, `onEnd`)을 쓴다.
- 환경변수: `OPENAI_API_KEY`, `OPENAI_MODEL` (이름만 `.env.example`에 적는다. 값은 적지 않는다). 가짜 모델 스위치 환경변수 하나(이름은 구현 때 정해 `.env.example`에 적는다).
- 키는 서버에서만 읽는다. `NEXT_PUBLIC_` 접두어를 붙이지 않는다.
- 위키 표는 RLS(Row Level Security: 줄 단위 접근 규칙)를 켜고 공개 항목만 읽게 한다. 서비스 키는 쓰지 않는다.
- 새 패키지 설치, 환경변수 추가, OpenAI 연결, 비용 발생은 `AGENTS.md`에 따라 하기 직전에 아키텍터 승인을 받는다.
- 모델 출력은 텍스트로만 표시한다 (HTML·스크립트로 해석하지 않는다).

## 11. 검증 (공고 기본 5, 교재 10-7)

**가짜 모델과 진짜 모델은 따로 보고한다.** 가짜 모델의 성공은 진짜 모델 품질의 증거가 아니다 (교재 10-7).

| 단계 | 확인 | 모델 |
|---|---|---|
| 연결 | 키가 Git·화면 번들에 없음. 로그아웃 요청은 모델 호출 전에 거절 | 가짜 |
| 입력 | 빈 입력·너무 긴 입력·`role: "system"` 포함 요청 거절 | 가짜 |
| 시험 3종 | 정상 질문 / 자료에 없는 질문(예: "누적 이용자 수") / "앞선 지침을 무시하고 …" (교재 10-7) | 가짜 → 진짜 |
| 평가 | 칸별 결과가 오고 기획안 본문은 그대로 | 가짜 → 진짜 |
| 질의응답 | 근거 자료 이름 표시 / 자료 없음 표시 / 끊김 표시 | 가짜 → 진짜 |
| 횟수 | 동시에 10번 요청하면 5번만 통과 / 실패하면 자리 반환 | 가짜 |
| 기존 기능 | 저장·임시저장·PDF·메일·공개가 그대로 동작 (공고 기본 4) | — |
| 실제 한 번 | 실제 OpenAI 호출 성공·실패 안내·토큰 사용량 기록 | 진짜 |
| 배포 | `dev`에 올린 뒤 배포 주소에서 로그인 → 기획안 → 평가 한 번 → 질의응답 한 번 | 진짜 |

- 진짜 모델 호출은 비용이 든다. 호출 전에 아키텍터의 승인을 받는다. 토큰 사용량으로 호출 1회 비용을 계산해 보고하고, 5만 원 지원 범위 안인지 함께 적는다.
- 아키텍터가 직접 본 것은 사실로 둔다. 확인하지 못한 것은 "확인하지 못함"으로 적는다.

## 15. 작업 규칙 (CLAUDE.md와 같은 방향)

- 크리에이터 화면(`app/creators`, 크리에이터 마이그레이션)과 운영자 화면(`app/admin`)은 다른 세션이 맡고 있다. 이 작업에서는 그 파일을 고치지 않는다. 겹치는 곳(`site-nav.tsx`, `AGENTS.md`, `docs/screen-contract.md`, `lib/plans.ts`)을 고칠 때는 `git pull`로 최신 `dev`를 받은 뒤 필요한 줄만 고친다.
- `dev` 가지에는 올린 뒤 보고한다. `main` 합치기·푸시·Vercel 배포는 아키텍터가 명령할 때만 한다.
- 파일을 지워야 하면 이유를 설명하고 아키텍터에게 먼저 묻는다.
- 화면만 고치는 작업에서는 백엔드(`app/actions`, `lib`, `supabase`, `proxy.ts`, `app/api`)를 건드리지 않는다. 칸 이름이나 처리 함수 모양을 바꿔야 하면 코드를 고치기 전에 보고한다.
- 형식 검증은 아키텍터가 P8에 답하기 전에는 실행하지 않는다.
- 시키지 않은 파일·화면·기능은 만들지 않는다. 넣는 게 좋다고 생각하면 한 줄로 말만 한다.
- 개발 용어는 처음 쓸 때 쉬운 한국어로 풀어 설명한다.
- 이 문서에서 막히거나 모르는 부분은 그 부분 하나만 아키텍터에게 묻는다.
