# 포트폴리오 화면 요구사항 (미션 7 단계 5)

새 세션이 이 문서만 읽어도 단계 5를 시작할 수 있도록, 계획 문서(저장소 밖)의 단계 5 내용과 이미 만들어 둔 바탕을 정리했다.
**먼저 `AGENTS.md`를 읽고, 구현 전에 계획을 세워 사용자 승인을 받는다.**

## 1. 상태

- 단계 0~4, 6은 `dev`에 구현·시험 완료. 단계 5(이 문서)와 단계 7(README·QA·배포 점검)이 남았다.
- **Figma 링크는 초안일 뿐이다.** 화면은 새로 설계한다. 시안을 읽는다면 색·글자·간격·배치의 근거로만 쓰고, 시안과 제품 요구가 충돌하면 임의로 정하지 말고 먼저 보고한다(`AGENTS.md`의 Figma 원칙). 토큰은 `AGENTS.md`의 디자인 토큰 표를 먼저 쓴다.

## 2. 만들 것

| 경로 | 내용 |
|---|---|
| `/portfolio` | 공개된 기획안 목록 |
| `/portfolio/[id]` | 공개된 기획안 상세 + 「협업 신청」 버튼 |

- **공개된 것만** 보인다. 공개를 취소했거나 삭제된 기획안 주소, 없는 id는 **404**.
- 보이는 것: 제목, 공개 이름, 공개한 시각(KST, `lib/time.ts`), 완성 로그라인과 쓴 내용(`plans.public_content`).
- **이메일은 어디에도 보이지 않는다.** 임시저장 이력·고른 선택지도 보이지 않는다(공개용 사본만 읽는다).
- 로그인 없이 누구나 볼 수 있다(검색엔진 노출 여부는 사용자에게 먼저 묻는다. 지금 `app/robots.ts`는 `/collab`만 막는다).
- 모바일·데스크톱 모두. 이미지가 필요하면 `AGENTS.md`의 「이미지 자리」 규칙을 따른다.
- **예시 기획안 1건**: 현재 로그라인 틀(사건·주인공·장애물·목표·위험)에 맞춘 **가상의 예시**를 초안으로 채워 두고 사용자가 검토한다. 실제 작품 설정은 만들지 않는다. (실제 회원 데이터를 흉내 내 DB에 넣지 말고, 방식은 계획 단계에서 제안한다.)

## 3. 「협업 신청」 버튼과 받는 사람

- 상세 화면의 「협업 신청」 → 협업 신청 폼(`/collab/new`). **받는 사람은 그 기획안의 주인**이다.
- **받는 사람 번호를 화면에서 받지 않는다.** 폼에는 기획안 id만 넘기고, **서버가 기획안에서 주인을 찾아** `recipient_kind='user'`, `recipient_id`, `plan_id`로 저장한다. **공개된 기획안만** 허용하고, 아니면 아클링스 앞 신청으로 되돌리지 말고 안내한다.
- 신청 화면 위쪽에 「이 신청은 ○○님께 전달됩니다」(공개 이름)를 보여 준다. 동의 문구에 이미 「신청 내용은 받는 사람에게 전달됩니다」가 있다(`lib/consent.ts`).
- 알림 메일은 **기획안 주인**에게 간다(주인의 확인된 이메일). 메일에는 신청자 연락처·내용을 싣지 않고 안내와 링크만 싣는다.
- 주인이 탈퇴해 기획안이 지워졌다면 신청을 받지 않는다(404/안내).
- 운영자 표시 계정도 **남의 기획안 앞으로 온 신청은 보지 못한다**(0003 RLS가 이미 막는다. 시험으로 확인한다).

## 4. 이미 있는 바탕 (다시 만들지 않는다)

- `plans.is_public`, `plans.published_at`, `plans.public_content`(공개 순간의 사본): `0004_plans.sql`. 공개된 것은 누구나 읽는 RLS가 이미 있다. 사본 모양은 `lib/plans.ts`의 `PublicContent`(`sections[{id,label,text}]`, `answers[{label,text}]`).
- `profiles.display_name`: 누구나 읽는 공개 이름(`0002`). 이메일은 `profiles`에 없다.
- `collab_requests.recipient_kind/recipient_id/plan_id`와 받는 사람 기준 RLS, 접수는 서버가 검사 뒤 서버 전용 열쇠로 저장: `0003`, `app/actions/collab.ts`의 `createCollab`(지금은 항상 `arklings` 앞). 알림 메일: `lib/collab-notify.ts`(`recipientKind`/`recipientId`를 이미 받는다. 회원 앞 메일 경로가 실제로 도는지 시험한다).
- 봇 방지(숨은 칸·횟수 제한)·파일 검사·동의 문구는 폼과 서버 동작에 이미 있다.
- 공개 취소 시 사본을 지우는 동작, 탈퇴 시 연쇄 삭제, 공개 안내 문구(「공개 이름이 함께 보입니다」): `/planner`에 이미 있다. 화면의 「포트폴리오(준비 중)」 문구는 이 단계에서 실제 링크로 바꾼다.

## 5. 확인 항목

- 비로그인으로 목록·상세가 열린다. 이메일이 어디에도 없다(화면·HTML 원문·요청 응답).
- 비공개·삭제·없는 id는 404. 공개를 끄면 목록에서 사라진다.
- 신청은 **기획안 주인에게만** 보인다. 다른 계정·운영자 계정은 못 본다(화면과 직접 요청 모두).
- 화면이 보낸 받는 사람 번호는 쓰이지 않는다(조작해서 보내도 무시). 비공개 기획안 id로 신청을 보내면 거절된다.
- 주인에게 알림 메일이 가고, 접수 확인 메일·봇 방지는 기존대로 동작한다.
- 모바일·데스크톱, 이미지 alt, 깨진 링크, Console 오류, `npm run build`·`npm run lint`.
- 시험은 가짜 이메일·가짜 값만 쓴다. 진짜 Supabase 키와 메일 설정은 환경에 들어올 수 있으나 시험에는 쓰지 않는다.

## 6. 위험 (보고에 포함)

- **제3자 전달:** 로그인한 누구나 받는 사람이 될 수 있어, 악의적인 회원이 자기 포트폴리오로 신청을 유도해 연락처를 모을 수 있다. 신청 화면에 받는 사람 공개 이름을 보여 주고 동의 문구에 전달 사실을 적는 것으로 줄인다. 신고·차단은 이번 범위 밖.
- **공개 이름:** 소셜이 준 이름(실명일 수 있음)이 처음 공개 이름으로 들어간다. 수정할 수 있다고 안내한다.
- 포트폴리오는 누구나 보는 화면이라 개인정보처리방침(`/privacy`)·동의 문구와 맞는지 확인한다. 실제 운영 전 전문가 확인 한 번.

## 7. 그 밖에 알아 둘 것

- 새 패키지·환경 변수·외부 서비스는 사용자 승인 후에만(`AGENTS.md`). 파일 삭제는 설명 후 허락받는다(훅이 막는다).
- `dev`에서만 작업하고 승인 없이 올린 뒤 보고한다. `main` 병합·푸시·배포는 승인 때만.
- 진짜 Supabase·구글·카카오·네이버 메일 확인이 남아 있다: `supabase/social-setup.md`, `supabase/mail-setup.md`.
- 사용자는 개발 용어를 모른다. 보고는 쉬운 말로, 영어 오류는 뜻을 풀어서, 끝에 남은 위험을 적는다.
